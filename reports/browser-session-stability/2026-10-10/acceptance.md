# 2026-10-10 managed Chrome：空闲读取和断线恢复验收

本轮先交付浏览器稳定性结果。用户已明确同意，完整票价验收暂留未通过。按北京时间归档，JSON 原始时间为 UTC。期间没有新增来源、迁移 Runtime 或扩展产品功能。

## 已确认的结果

空闲后两次真实正文读取都成功，耗时 26.415 / 12.855 秒。首次请求时 daemon 和 CDP 均不可用，socai 自动启动同一个 managed profile，约 4.198 秒后观测到连接。第二次在无 keepalive 的 30 秒空闲后复用连接。用户确认两次都没有调试授权弹窗，也没有要求重新登录。不能据此声称持续空闲了三小时：首次请求之前的空闲时长没有受控记录。见 [空闲读取](idle-read.json)。

先做一次完整研究，再做五次真实断线测试。修复前一次没有进入恢复；修复后四次都自动续跑同一个 Session / Turn。已完成的社区查询没有重跑，原正文与观察时间保持不变。首次修复后的重连也由用户确认没有再次授权或登录；后续几次未逐次补问，不能用 CLI 状态代替弹窗观察。

最后一轮在已有一个精确日期、3 个真实报价后关闭专用 Chrome。断线前这 3 个报价的 ID、金额、币种、来源和观察时间全部保留；精确日期记录也保留。暂停时独立完成的日期记录继续保留，续跑没有新增日期或验价请求。见 [最终观察记录](precise-fault-observation.json)。

最后一轮首条结果在 40.460 秒出现，前三条在 51.955 秒出现；总耗时 117.982 秒，最终 6 篇正文、5 条有报价路线。研究仍为 `partial`，不是完整月度票价验收通过。

## 为什么要改代码

修复前，专用 Chrome 在 20:57:50.522 UTC 关闭，WebSocket 在 20:57:50.564 记录终止；daemon 直到 20:57:55.485 才报告连接丢失。这约 4.9 秒内，`browser_connected` 仍为 true。FareScout 把来源失败记成普通 `CLI_FAILED`，继续尝试搜索，没有进入原轮次恢复。正文保住了，但恢复失败。

现在 `connection_observation` 同时保留 daemon 原始的 `reported_browser_connected` 和用于研究的 `browser_connected`。它核对当前 daemon PID、最新终止事件、先前健康观察以及重新建立连接的日志。若当前 WebSocket 已结束而 daemon 尚未更新，先标为断线并记住这个状态；旧 PID、旧终止日志和后来的新连接不会误触发断线。没有 INFO 级别的连接建立日志时，也可用断线之前的健康观察识别新的终止事件。

来源适配器用这个状态把传输失败归为 `BROWSER_DISCONNECTED`。工作台保留 checkpoint，等 daemon 确认未连接之后再用掉本轮唯一一次自动重连机会。socai 随后启动或复用同一个 profile；连接可用后继续未完成步骤。没有 `socai stop`、全局进程清理或 profile 删除。当前 daemon PID 11617 在所有受控 Chrome 关闭前后均保持不变。

这解决了“状态还没更新，应用已错过恢复”的问题，不能证明所有自然断线的根因，也不保证 WebSocket 永久保持连接。没有新的首次终止日志时，仍按实际 CLI 状态和失败结果处理。

此外，研究完成判断只计入正文读取完整的社区步骤，避免部分读取误算成完整查询。本机启动脚本增加可选 `FARESCOUT_NODE_BIN`，解决桌面启动环境找不到 Node、FlyAI 实际未启动的问题。`NODE_NOT_INSTALLED` 会明确提示配置，并在本段日期探索中停止重复调用。

前两次断线注入时没有成功日期，旧脚本的空集合比较不能当作日期保留 PASS，公开记录已补充范围说明。“范围线索后断线”那轮在断线瞬间也只有范围返回日期；独立日期工作在社区断线后完成，再验证暂停到续跑的保留。最后一轮已修正门槛，只在精确验价成功后注入断线，范围线索和同日报价复用不会充作额外日期。

重连耗时包含启动浏览器和一次只读搜索，不等于纯 WebSocket 握手时间。从实际关闭 Chrome 到开始续跑，四轮分别为 20.176、38.931、35.155、28.607 秒。后几轮在社区暂停期间继续完成已经开始的日期工作，随后再恢复社区。总耗时包含等待；`execution_seconds` 只累计实际研究段，不能混作总耗时。

## 调用量和阶段耗时

最后一轮实际模型请求 10 次，社区适配器调用 5 次，研究内 socai CLI 19 次，恢复另有 6 次 CLI 命令。日期来源调用 16 次，最终独立验价请求 0 次，同轮同条件报价复用 5 次。复用保留原抓取时间，不能算新增实时请求。

`date_calls` 和 `verification_calls` 统计适配器调用，不等于供应商账单请求数。前三轮 FlyAI 受 Node 缺失影响，部分计数对应失败启动，未真正访问票价接口。验收脚本调用 `/api/browser` 的独立状态核对不计入研究的 `socai_commands`。空闲检查来源内 CLI 为 15 + 4 次，另有前后取样 `status` 共 4 次。

最后一轮社区搜索累计 43.222 秒、扩展搜索 23.665 秒、模型操作 23.293 秒；日期阶段实际经过 28.923 秒，日期请求耗时相加为 36.326 秒。正文读取是社区阶段的子步骤，不能重复相加；日期与社区工作有交错，阶段之和也不等于总耗时。逐轮完整统计见 [summary.json](summary.json)。

## 复现

先按 [README](../../../README.md) 配置本机模型与现有来源，在 managed 专用窗口首次登录一次。不要把 profile 放在 iCloud 中，也不要在测试前清理登录态。

```sh
FARESCOUT_DATA_DIR=data/recovery-live ./scripts/run-this-machine.sh serve --port 8768
# 另一个终端：会真正关闭一次该 profile 的专用 Chrome。
PYTHONPATH=src .venv/bin/python scripts/managed-research-acceptance.py \
  --session my-managed-recovery \
  --inject-disconnect --allow-managed-chrome-close \
  --min-precise-dates-before-fault 1 \
  --output data/my-managed-recovery.json
PYTHONPATH=src .venv/bin/python scripts/export-research-audit.py \
  --session my-managed-recovery --data-dir data/recovery-live \
  --output data/my-managed-recovery-audit.json
```

脚本先核对本地配置与工作台的 daemon PID，再匹配 Chrome 主进程和完整 `user-data-dir`，发送 SIGTERM 前重新检查 PID。找不到唯一进程或 profile 不一致就停止，不关闭其他浏览器。没有精确日期成功或没有正在执行的社区动作时，不注入断线；这种情况不会算恢复通过。观察超时只保存结果，不取消研究或修改 checkpoint。CLI 不能识别授权弹窗，需要人工记录是否出现。检查并脱敏测试记录后再公开提交。
