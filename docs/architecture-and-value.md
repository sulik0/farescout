## 1. FareScout 想解决什么问题

传统机票搜索通常要求用户先知道目的地、日期和行程，再在这些条件下找价格。用户说“深圳香港最近有什么便宜国际机票”时，真正缺少的是**应该查哪些目的地和航线**。FareScout 先把社区讨论当成发现线索，再对少数候选调用实时票价来源；它交付的是带出处、当次报价和限制条件的**调查方向**，而非下单承诺或“全网最低价”。

这形成三个相互独立的判断：

1. **有人在讨论什么**：帖子正文和评论中的目的地、航司、促销、晒价及反对意见。
2. **现在能查到什么**：指定日期、机场、人数和舱位的实时航班报价。
3. **这些信息能否放在一起比较**：单程/往返、币种、税费、行李、日期和航段是否对齐。口径不一致就并列展示，不计算虚假的节省金额。

## 2. 系统怎样从用户提问走到研究报告

```mermaid
flowchart LR
    U[模糊需求或追问] --> G[目标与会话上下文]
    G --> Q[模型生成宽查询]
    Q --> S[socai 读取小红书正文和评论]
    S --> E[标准化社区证据]
    E --> D[模型提取候选与扩展查询]
    D --> V[逐字引用及航线校验]
    V --> X[根据已读线索再次搜索]
    X --> E2[重新提取并筛选最多 5 条候选]
    E2 --> F[FlyAI / SerpAPI 按具体条件验价]
    F --> C[核对航段、日期、舱位和价格口径]
    C --> R[确定性生成报告与保存会话]
    R --> U
```

图中的回环表示两件事：系统会**根据本轮读到的证据提出新查询**，也会在用户追问时继续使用此前的研究内容。系统不会无限搜索：通常先做 2 次较宽的查询，最多再扩展 1 次，最多核查 5 条候选路线，精确验价默认不超过 10 次；每个来源和整轮研究都有超时限制。没有证据或验价失败时允许输出部分结果，不用模型知识补造价格。

| 阶段 | 当前实现 | 产物与判断边界 |
|---|---|---|
| 理解需求 | [`evolve_goal` 与 `Brain.patch`](../src/farescout/research.py)把输入转成出发机场、地区、日期窗、单程/往返、红眼限制；默认假设写入报告 | `Goal`。追问只改本轮明确条件，继续保留原研究范围 |
| 宽搜索 | [`Brain.plan`](../src/farescout/research.py)产生不同的社区搜索词；模型失败时用基于目标的保底查询 | 搜索词，不是预设的“便宜航线榜” |
| 社区研究 | [`Socai.search`](../src/farescout/providers.py)调用现成 `xhs search`，打开帖子读取正文与评论；v0.6.1 的 `notes[].entity`、`top_comments` 被归一化为 `Evidence` | 有来源 URL、查询词、原文、发布时间原文和读取时间；只有标题卡片不计入证据 |
| 发现与扩展 | [`Brain.discover`](../src/farescout/research.py)从已读证据提取航线、逐字摘录、晒价、航司及新的查询词；扩展后再次提取 | `Candidate`、`Signal`、`Expansion`。新查询必须引用证据 ID，其关键线索必须出现在已读正文/评论里 |
| 筛选 | [`grounded`](../src/farescout/research.py)核对引用、机场/国家、地区约束、日期提示，去重后按发帖新近程度和证据多样性排序 | 最多 5 条有来源的候选；词表只辅助地名归一化，不提供价格或预设低价路线 |
| 实时验价 | [`FlyAI` 与 `SerpAPI`](../src/farescout/providers.py)按候选机场、样本日期、1 成人经济舱发只读请求，逐个尝试 | `Fare`；检查返回航段、机场、出发日、单程/往返和红眼要求。某来源失败时继续另一来源 |
| 证据综合 | [`synthesize` 与 `render_report`](../src/farescout/report.py)由代码生成价格摘要、出处、限制和事件表 | 社区晒价与当前报价分栏；不同税费口径不合并成一个价差；每个渠道只展示代表性最低报价，完整匹配报价留在会话 JSON |
| 持久化与续跑 | [`Researcher`、`Store`](../src/farescout/engine.py)保存目标、原文、候选、报价与失败事件；可从已有会话继续 | 多轮追问重筛候选并重新验价，不把旧报价假装成当前报价；宿主桥接模式可收取匹配的迟到回执 |

日期没有精确信息时，程序会在声明的窗口内选**一个样本日**做验证。它没有扫描全月价格日历，因此报告只能说“这天查到”，不能说“最近最低”。城市级社区线索映射到具体机场时，报告也标明这是验证样本，不声称帖子原本指定了该机场。

## 3. Agent 在研究中会做什么

FareScout 是一个会在预设步骤和调用范围内开展研究的 Agent（智能体）。复用 [Pydantic AI](https://ai.pydantic.dev/) 的模型调用、按指定格式生成结果、校验结果并在必要时重试。模型不能随意操作浏览器或运行命令；程序规定了研究步骤和工具权限，模型在这些步骤中决定接下来查什么。

| 模型作出的决定 | 程序施加的约束 | 为什么属于研究能力 |
|---|---|---|
| 把“深圳香港最近”转成可继续的目标，并理解“日本呢、11 月呢、不要红眼”是对同一任务的修改 | 类型校验、日期窗与机场规则；保留会话中的原始证据 | 不要求用户一次填完机票搜索表单 |
| 先提出宽查询，再从已读正文中发现用户没点名的亚庇、槟城、河内等方向 | 候选必须引用现有证据，逐字摘录需在正文/评论出现，航线地名需可核对 | 目的地来自读到的内容，不是从预先准备的热门目的地清单中挑选 |
| 根据“香港快运”“亚庇”等新线索形成更具体的查询，并在读到新帖子后调整候选 | 扩展词须出现在所引证据与查询中；查询次数有明确上限 | 下一步调查由已有发现决定，而非一组固定搜索词 |
| 从多个帖子里选少数值得验价的方向 | 最多 5 条；发布时间与独立证据数影响排序；模型不能创建当前价格 | 从大量线索中选出可以继续查证的路线 |

真实独立运行中，模型先提出“深圳香港出发国际机票”“深圳香港飞国外便宜机票”，socai 读取社区内容后，模型又提出“香港快运 亚庇 10月 单程 特价 日期”；第二次发现阶段最终产生 5 条验价方向。该轮共保留 12 篇不同的社区正文，5 条方向均取得报价，4 条同时获得两个票价渠道支持，首轮耗时约 **3 分 18 秒**。追问“日本呢 → 11 月呢 → 不要红眼”共用同一研究会话，并重新验价。详见[本次真实证据](acceptance.md)。

**模型不担任事实来源。** 社区原文来自 socai，当前报价来自票价接口，价格解析、航段匹配、口径区分和最终报告均由确定性代码完成。模型返回的不实引用、不在原文中的晒价或不符地名会被剔除；当前报价只能由票价适配器写入 `Fare`。当前也没有跨网站无限规划、自动学习最优搜索策略或自主交易能力。

## 4. 复用了什么组件，为什么选择它们

| 组件或参考 | 本次实际使用方式 | 选择原因与取舍 |
|---|---|---|
| [Pydantic AI](https://ai.pydantic.dev/) | 结构化 `GoalPatch`、`SearchPlan`、`Discovery` 模型输出；兼容已配置模型 API | 只需要小型、有类型约束的研究推理，避免为了 POC 搭建整套执行平台。工具编排与停止条件由 FareScout 自己控制 |
| [socai](https://github.com/socai-io/socai) | 实际使用 v0.6.1 的只读小红书搜索、正文和评论读取，复用用户已登录的 Chrome | 社区页面、登录态及内容读取最难稳定自研。只接收真正读到正文的记录；不搬运 Cookie 或重建社媒抓取器 |
| [FlyAI](https://github.com/alibaba-flyai/flyai-skill) | 官方 CLI 的结构化航班查询；本机实测体验模式 | 以少量精确路线和日期直接获取真实航班；适配器兼容实测 `ticketPrice` 和示例 `adultPrice`，但将其税费标为未知 |
| [SerpAPI Google Flights](https://serpapi.com/google-flights-api) | `google_flights` 查询，带机场、日期、CNY、1 成人、经济舱、`no_cache` | 为候选提供另一真实验价渠道；此次单程响应作为含税总价展示。往返尚未完成 `departure_token` 回程确认，因而不把首段价伪称完整往返价 |
| [宿主 Browser Harness 桥接](browser-bridge.md) | 早期作为可选宿主浏览器回执路径；独立成功运行不依赖它 | 登录后的侧边栏浏览器无法直接供 socai CLI 使用时，借用已有浏览器能力完成只读验证；文件回执只传研究结果，不传登录态 |
| [OpenCLI](https://github.com/jackwener/opencli)、[Prism travel-agent](https://github.com/Prism-Shadow/travel-agent) | 仅参考 Chrome 集成、浏览器可见操作、观察后验证和标签页边界 | P0 的 socai + 两个票价来源已足以验证链路，未再引入第二套浏览器基础设施，也未 fork 预订流程 |
| [DeepSeek Harness](https://www.deepseek.com/harness/en/)、[huahuanao travel-agent](https://github.com/huahuanao/travel-agent) | 分别参考 Agent 执行设计和“社区线索 × 当前价格 × 出行现实”的不同来源各自提供社区线索、当前价格或出行信息 | 保留研究方法，避免把更广的平台、预订或旅行规划功能一起搬入 POC |

FareScout 自己编写的代码负责把这些组件连起来，并判断哪些路线值得继续查。它会保存多轮目标、证据和候选路线，核对引用原文，根据已读证据扩展查询；某个来源失败时继续尝试其他来源，并按相同条件筛选和解释报价，最后保存会话、生成报告。这些决定了产品是否真正回答“有什么值得我进一步看”，而不是简单把第三方输出拼在一起。

## 5. 怎样使用真实数据、保护用户信息并处理失败

- **社区与票价分别建模**：`Evidence.kind=community`，`Fare.kind=current_verified`；社区的“晒价”永不提升为当前价。所有证据保留读取时间；只有可引用的正文/评论进入候选抽取。
- **报价按请求校验**：解析来源响应后，核对实际机场、航段连续性、日期、舱位和行程类型。用户说“不坐红眼”时，按每段当地 22:00–06:00 或跨夜保守排除。该规则可能误排某些长途正常航班，报告注明限制。
- **口径不确定就不计算差价**：FlyAI 的税费总额未确认，SerpAPI 的含税价与它并列展示。社区中的往返、退税后、活动价和当前单程样本也不合并。
- **失败继续，但不虚构**：socai 失败可尝试配置的公共社区备用来源；FlyAI 对某条路线失败会继续试 SerpAPI。本次巴厘岛 HKG→DPS 就发生了这一情况。来源都失败时保留已有证据并标记未验证；验证码、登录障碍或访问限制不绕过。
- **限制权限与预算**：只开放研究命令、只读 API，模型没有 shell 或交易工具；子进程不继承无关 API Key。URL 去掉查询参数及可能的访问 token；`.env` 和运行时 `data/` 不进入交付包。每轮有来源超时、总时限和精确验价次数上限，不进入乘机人填写、锁座或支付。

完整记录以本地 JSON 保留每个来源的结果与错误事件，Markdown 报告只呈现能说明机会和限制的内容。早期宿主浏览器路径由[`bridge.py`](../src/farescout/bridge.py)实现读回执与超时续跑；主路径使用 socai。运行命令和登录方式见[README](../README.md)。

## 6. FareScout 的价值和仍待验证的问题

**FareScout 要把“我不知道该搜哪里”变成“我有 3～5 条有出处、能查到当前报价、条件也说清楚的路线”。** 这减少了用户先刷社区找灵感、再猜航线搜索、再辨别过期促销的重复劳动。传统机票搜索通常从用户已经知道的目的地开始；FareScout 还会从社区帖子中发现用户没想到的路线。它也不止总结帖子内容，而会查询当前票价，并说明哪些价格不能直接比较。

本次 POC 提供了具体证据：对一个未指定目的地的输入，在约 3 分 18 秒里读 12 篇正文、完成一次基于已读内容的查询扩展，并给出 5 条有当前报价的调查方向。它验证了**研究闭环可以运行**，并表明本次耗时低于用户提出的“刷半小时”参考时间；尚未对同一任务进行人工作业对照、盲评机会质量或多日重复稳定性试验，因此不宣称已经证明“总能比人找得更好、更快”。

当前仍缺少全月价格扫描、历史/典型价格基线、行李和深圳到香港机场交通成本归一化；机场词表覆盖有限，因此可能漏掉较少见的航线。社交内容的促销可用性、报价库存和接口配额随时间变化。下一阶段若要判断真实用户价值，应记录新目的地发现率、用户原本不知道的有效航线比例、当前报价可复现率、从输入到可行动建议的用时，以及用户对“值得关注”的人工评价；这些指标现在尚未建立正式对照基线。
