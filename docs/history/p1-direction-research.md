# FareScout P1：后续方向调研与优先级建议

调研日期：2026-10-01。本文记录当时的开发建议，**撰写时尚未实现 P1 功能，也没有付费调用新接口查询真实航线**。POC 的产品需求与验收仍以[原始需求](../current/product-requirements.md)为准；现状以[实现说明](../current/system-overview.md)和[独立验收记录](p0-acceptance.md)为准。原需求把 Typical Price / 简单 Deal Strength 放在 P2；本次用户建议将基础版提前到 P1，属于明确的后续优先级调整，不应倒写成 POC 已具备此能力。

## 调研结论

五项 P1 方向合理，最直接的用户价值是把“11 月某一天查到 ¥X”推进到“11 月哪些日期值得看、当前价相对通常水平如何”。建议保留 **Flexible Date Discovery 为首个用户可见成果**，但应先补上两项共用基础：记录用户提出的条件及系统的解释，并用固定字段记下每一步研究操作。否则日期探索会在“最近/11 月/不要红眼”的含义不清时扩张请求量，Trace UI 也只能展示模糊日志。无需迁移 Agent Runtime 或引入 Multi-Agent。

另一个战略判断：Google Flights 已有用自然语言寻找机票 Deal 的实验功能，也会按类似行程的典型价格判断优惠。因此 FareScout 的差异不宜定义成“自然语言 + 低价票价 API”；更强的定位是**从中文社区发现用户不知道的路线与促销线索，再用当前报价验证，展示信任依据与失败边界**。[Google 对 Flight Deals 的说明](https://support.google.com/travel/answer/16497283?hl=en)

## 四个方向分别要解决什么问题

| 方向 | P1 要解决的问题 | 本阶段暂不处理的内容 |
|---|---|---|
| Research Intelligence | Agent 根据研究中发现的情况决定下一步：线索不足就继续搜索社区；日期不明确就先探索日期；两个来源的结果冲突或帖子说得含糊，就针对疑点再核查；调用额度用完或新证据已经很少改变判断时，就停止。每一步都记录为什么要查。 | 继续使用单个 Agent，并限定它能做的操作和调用次数，不让它无限浏览，也不迁移整套运行环境。 |
| Deal Intelligence | 同一行程的当前价格、可比的典型区间/来源 Deal 标签、促销条款并列展示；区分“绝对价低”“相对通常便宜”“仅有社区热度”。 | 无能够公平比较的参考价格就只称“值得调查”；不根据 FlyAI 税费未知价格计算节省比例，也不做复杂总成本分数。 |
| Source Intelligence | 不同来源提供不同信息：社区帖子提供线索和用户体验，航司官网说明促销规则，票价服务返回当次可查询的报价。接入新来源前，先说明它能帮助核实什么。 | P1 先完善已有小红书和两票价源。只有社区线索指向具体航司活动时，才考虑一次定向官方核查；抖音/公众号全面接入延后。 |
| Explainability | 用户能看到需求怎样被解释、每次搜索怎样影响候选、为何验价、冲突为何无法相减，以及何时停止。 | Trace 必须来自真实事件和引用关系，不能让模型事后编写“思考过程”。不展示模型私有推理。 |

当时的 POC 通常会进行两次范围较宽的社区搜索，根据帖子线索再查一次，最多保留五条候选路线，并在一个样本日期查询票价；精确验价默认最多调用十次。研究报告中能看到事件列表，但界面还不能实时展示每一步的详细记录。多轮对话会继续使用已读证据并重新查价，不过仍需更仔细地判断旧帖子是否适用于当前行程。[代码：研究循环](../../src/farescout/engine.py)、[数据模型](../../src/farescout/models.py)、[验收记录](p0-acceptance.md)

## 五项 P1：建议怎样实现、怎样验收

### 1. Flexible Date Discovery：先粗筛，再精确验证

给每个候选一个明确的日期窗、单程/往返、停留天数及筛选规则。第一步在窗口内找少量“可能便宜”的日期；第二步对这些日期调用现有精确航班查询，校验实际机场、航段、当地时间、舱位和报价时间；第三步仅在通过限制后比较。明确列出查过哪些日期、还有哪些日期没有查，**如果只查了少数日期，就不能称为“全月最低价”**。当候选有 5 条、两个出发机场且跨一整月时，不能做无上限的路线 × 日期 × 来源笛卡尔积；需要每轮查询预算和停止条件。

官方接口资料给了三条可选路径：

- [FlyAI 官方 CLI 文档](https://github.com/alibaba-flyai/flyai-skill)列出 `--dep-date-start/end`、`--back-date-start/end` 及按价格排序。它适合作为**已知路线**的范围粗筛候选，但是否一次返回足够完整日期、海外路线覆盖及限流表现，尚须对深圳/香港样本实测。
- [SerpAPI Google Travel Explore](https://serpapi.com/google-travel-explore-api)可以按出发机场、到达地区/城市、月份和预设停留时长探索；灵活月份只覆盖未来六个月，停留选项为周末、1 周、2 周。它适合目的地和大致月份发现，未必能精确表达“11 月任意 5 天”。
- [SerpAPI Google Flights Deals](https://serpapi.com/google-flights-deals-api)支持出发日期范围、单程、往返及往返停留长度，返回日期、路线、价格、部分平均价/折扣和精确航班链接。它可做小范围候选日期与 Deal 线索探索，但目前文档未证明 SZX/HKG 出发覆盖和结果完备性，需单独 spike；不能让它替代社区发现。现用的[Google Flights 精确接口](https://serpapi.com/google-flights-api)针对单程/往返要求具体 `outbound_date`，仍用于最终复验。

**验收**：输入“11 月日本什么时候便宜”，对至少三个有社区证据的候选展示窗口内多个**实际被检查**日期、每个机会的最终具体行程及查询时间；“不要红眼”后的结果只在满足规则的航班中比较；所有探索价与最终验价分层标注；记录调用量、耗时和没有查到结果。先用固定样本与人工 Google Flights 日期网格核查召回，不预设“全月最便宜”指标。

### 2. Research Trace UI：先事件，再界面

现有 `Event` 只有时间、stage、source、status、detail，并通过回调即时输出、整轮会话落盘。P1 应先约定机器可读事件：`turn_id/action_id/parent_action_id`、动作类型、输入约束快照、来源、引用的 `evidence_id`、开始/结束/失败、耗时、结果数量、预算消耗和候选去留原因。UI 再按“用户需求 → 搜索/阅读 → 扩展 → 日期探索 → 精确验价 → 冲突 → 结论”呈现，可折叠原文与失败细节。候选不能只显示最终命中，还应显示被舍弃原因；否则轨迹会误导用户以为没有搜索其他方向。

**验收**：运行中可见状态更新；重新打开已完成会话能够复原同一轨迹；每个最终机会能追到帖子摘录、验证请求和来源结果；失败、没有查到结果及停止原因同样可见。Trace 不显示 API Key、浏览器登录信息或模型未验证的推理文本。

### 3. Post / Evidence Quality：先证据标签，再排序

给帖子/评论建立可审查的特征：原文是否真正读到、发布时间与旅行/促销适用日期、是否有明确机场/航司/日期/价格口径、是否指向官方活动、是否有广告/代理/导流信号、图片关键信息是否尚未读到，以及与其他帖是否同一素材的转发。两篇复制文案不能算两个独立来源；两条评论也不能自动提升为独立佐证。商业信号应作为**风险标签**而非自动断言“虚假”，避免误杀有效促销。

**验收**：先人工标注一小批真实帖子，检查“可用线索”和“商业/过期/重复”标签的准确性与遗漏案例；候选页面说明哪些证据支持这条路线、哪些信息会降低可信度；低质量帖仍可作为搜索线索，但不能独自支持“有当前 Deal”。

### 4. Semantic Constraint Visibility：把解释权交给用户

把每项约束按固定字段保存，并标出来源：用户明确说的、从语境推断的、系统默认的。例：“最近”映射的具体起止日应显示为默认/推断；“11 月”要显示年份与起止日；“日期无所谓”表示允许宽窗探索，仍受可用航班时段、接口覆盖与查询预算限制；“不要红眼”目前是**任一航段当地 22:00–06:00 或跨夜就排除**的保守规则，不应只用一个 `true` 隐藏。用户修改规则后，要能看到哪些候选和价格因此发生变化。跨夜长途可能被过度排除，须明确展示该取舍。

**验收**：对“深圳香港最近有什么便宜国际机票 → 日本呢 → 11 月呢 → 不要红眼”逐轮列出原文、解析值、来源和实际生效范围；改动后重新计算，报告与 UI 一致；日期不明确时不得悄悄改成另一个口径。

### 5. Deal Strength 基础版：分层结论，避免假精度

[SerpAPI Google Flights Price Insights](https://serpapi.com/google-flights-price-insights)文档列出 `lowest_price`、`price_level`、`typical_price_range` 和 `price_history`。同一家供应商的 [Flights Deals](https://serpapi.com/google-flights-deals-api)可返回部分 `average_price` / `discount_percentage`；这些字段并非每条都有，也不代表 FareScout 已获得完整历史价格库。Google 对其 Flight Deals 的说明是按类似行程过去 12 个月观察到的低价中位数，并考虑时节、停留、舱位及部分筛选条件；这是 Google 产品的计算说明，**不能无条件套用到 SerpAPI 每个字段的含义或假定两个接口基线相同**。[Google 官方说明](https://support.google.com/travel/answer/16497283?hl=en)

推荐输出三档：**有同条件数据可以核对当前价低于典型区间**、**绝对价可关注但缺可靠基线**、**当前未验证/证据不足**。只有同一来源、相同出发/到达、单程/往返、日期条件、舱位、人数、税费口径匹配时才显示相对典型价的数值比较；口径不齐时展示原因。不要把“社区晒价 ¥899”放进当前价分母，不要把 FlyAI 税费未知价和 Google 含税区间相减。

**验收**：对有 Price Insights、无 Insights、FlyAI/Google 口径冲突、促销失效四类样本给出不同且可追溯的结论；缺少字段时明确说明无法判断，不自行估算；UI 明确“典型价来源、比较条件、取得时间”。

## 建议的开发顺序

| 次序 | 交付片 | 为什么在这里做 | 进入下一片的门槛 |
|---|---|---|---|
| 0 | 用最少字段记录用户约束和研究事件 | 五项 P1 都会用到；先记录日期范围、行程、红眼规则、每一步的前因后果和引用来源 | 四轮多轮例子可重放，每条事件都能对应到实际操作 |
| 1 | Flexible Date Discovery | 直接补 POC 最大产品缺口 | 多日期被真实检查、精确复验、预算与覆盖边界可见 |
| 2 | Research Trace UI | 让日期探索和 Agent 动作可理解，也便于排查失败 | 运行中和历史回放一致，结论可回溯 |
| 3 | Post / Evidence Quality | 降低社区噪声造成的无效验价 | 人工标注样本中漏判/误判可复盘 |
| 4 | Semantic Constraint Visibility 完整编辑体验 | 在有真实日期/红眼结果后，用户能理解修改效果 | 编辑后追问与报告一致 |
| 5 | Deal Strength 基础版 | 需要先有具体日期和可公平比较的价格 | 没有可比价格时明确说明；有参考价格时列出判断依据 |

这里的“0”是底座，**不另开大架构项目**；用户提出的五项产品优先级仍按 1→5 推进。Research Intelligence 随每片逐渐增强：Agent 在候选不确定时做日期/来源/社区的下一步选择，但每个决定有目的、证据、预算及停止理由，而非为了展示“自主”而增加搜索次数。

## 开发前需要验证的事项和当前风险

1. 用少量只读样本比较 FlyAI 范围查询、Travel Explore、Flights Deals 在 **SZX/HKG → 日本与东南亚、2026-11** 的返回覆盖、日期精度、税费口径、耗时、没有查到结果和配额消耗；再决定日期粗筛的主/备路径。现在仅核对了文档，**不宣称新接口已经实测可用**。
2. 为 Price Insights 统计这些路线的字段出现率，核对 `price_history` 的适用行程及时间意义。不能从文档中的示例 JSON 推断每条查询都有历史数据。
3. 从现有真实会话取出带链接的帖子做人工标注，建立 Evidence Quality 的基线；否则规则很容易把“付费推广”和“有效低价线索”一并丢掉。
4. 用同一任务做人工对照：记录用户原本不知道但最终可验价的航线比例、从输入到可行动建议的时间、报价复现率、受约束候选正确率和用户对解释的信任程度。现有首轮 3 分 18 秒证明链路能跑，**没有证明机会质量优于人工半小时研究**。

最大的综合风险是**探索结果与可执行报价之间的落差**：灵活日期接口可能给出展示价或不完整覆盖，具体航班、库存、税费和红眼规则复验后可能消失。其次是 API 调用次数增加，以及社区里出现广告或过期信息。两者都应在 Trace 中被保留为失败或不确定性，而不是从最终报告抹掉。

继续暂缓：抖音/公众号全面接入、DeepSeek Harness 迁移、交通/行李成本归一化、复杂 Deal Score、Multi-Agent、更多 OTA、自动购买及完整历史价格库。
