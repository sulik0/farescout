更新日期：2026-10-04。本轮继续使用原有 Pydantic AI、socai 0.6.1、FlyAI、SerpAPI、Session 和 Evidence，没有新增数据源。实施范围见[本轮计划](research-recovery-plan.md)。

## 当前结论

代码已经支持在同一轮恢复研究、让日期验价与社区读取同时进行，以及让 Agent 按当前缺口选择下一步。98 项自动化测试通过，其中新增 14 项检查恢复、连接分类、任务取消、引用检查和结果计时。这些测试使用可控制的测试来源，不能替代真实来源验收。

真实验收尚未通过。两个中间版本的新进程研究都得到两条有社区引用和当前报价的结果，状态为 `partial`；之后一次新进程研究在原 CDP 会话断开后无法重连，状态为 `blocked`。没有取得三条结果时，`third_result_seconds` 保持缺失，不能写成 0 秒，也不能把两条结果计作完整通过。

## 本次断线能确认什么

用户实际观察并批准了首次远程调试弹窗。之后的两轮社区研究使用同一 daemon 和 endpoint。后续是否又出现弹窗，必须由用户观察确认；`browser_connected=true` 不能代替弹窗计数。

- 最近一次成功连接观测：2026-10-04 11:32:50（北京时间）。
- daemon 在 12:48:22.816 报告 `CDP session is closed`。
- macOS 电源记录在 12:48:23 报告因 `Idle Sleep` 进入睡眠。时间紧邻，支持继续调查睡眠影响，但还不能证明因果。
- 17:07:10 再次研究时，daemon PID 仍为 7976，Chrome PID 仍为 46958，endpoint 指纹仍为 `b5eb7c8be2ef259c`；`browser_connected=false`。
- socai 尝试重新连接，但约 61 秒后返回连接失败。备用 Reddit 连接也超时，因此没有正文可供提取。

这些记录说明“daemon 进程还在、endpoint 文件没变”不代表原 CDP 连接仍有效。没有证据显示 FareScout 杀死 daemon 或 Chrome。程序只结束自己的 CLI 客户端，不执行 `socai stop`、浏览器退出、登录态迁移或 profile 复制。

已核对 **v0.6.1** 官方源码：[daemon](https://github.com/socai-io/socai/blob/v0.6.1/cli/src/daemon.rs) 的空闲退出阈值为 24 小时，`status` 不更新任务活动计时；[运行时](https://github.com/socai-io/socai/blob/v0.6.1/core/src/runtime/engine.rs) 的 90 秒空闲释放只适用于远端托管浏览器，不适用于本次 `existing` 本机 Chrome；[CDP 生命周期](https://github.com/socai-io/socai/blob/v0.6.1/core/src/cdp/lifecycle.rs) 在连接建立后每两秒检查目标列表，连续三次失败会记录断开。因此再增加 FareScout 的网页轮询，不足以保证睡眠后不丢失会话。

Chrome 官方说明：请求新的远程调试会话时会再次询问用户许可，不能把第一次许可当作永久许可。[Chrome 的会话授权说明](https://developer.chrome.com/blog/chrome-devtools-mcp-debug-your-browser-session)。本轮没有修改 Chrome 安全设置。

## 程序现在怎样处理

1. 状态检查只读 daemon 状态，记录 PID、endpoint 指纹、连接变化和可识别的传输错误。未连接时授权状态写“未知”；无法确认的断线原因不写成已查明。
2. 当前轮连接失败后停止这个社区来源，保留正文、候选、失败和报价，尝试已有备用来源。恢复操作继续同一个 Turn，不增加新提问轮次。
3. 成功的查询和已读帖子不重读；已完成的日期探索不重扫。旧报价保留取得时间，超过复用时间后仅重新验选定日期。失败来源仍可在恢复后的新一段再次尝试。
4. 首批正文取得后，日期任务开始运行；社区读取保持串行，票价调用受共享预算和并发上限约束。研究退出前等待或取消日期任务，防止结论之后再出现迟到报价。
5. Agent 可选择继续社区查询、探索日期、在原社区核查促销或停止。只有存在多个有效选择时才调用模型；程序拒绝不在当前可执行范围内的选择，并检查预算和原文引用。
6. 实测中，活动帖子列出多个日本航点却没写香港出发，导致候选不足。现在把缺少出发地的原文列为下一步查询的已知缺口；获得正文确认之前仍不把这些航点计作香港出发路线。

## 已验证的真实报价恢复

在 Chrome 重连仍等待人工处理时，明确关闭社区适配器，仅用已有部分研究验证恢复行为。这不是小红书重连后的完整验收。

第一次恢复 `recovery-final-1` 保留了同一 Turn、原文时间和日期调用量，实际增加4次验价、用时7.218秒。但它暴露出旧缓存重新排序后改变选定日期的问题（东京从11月14日变成11月30日）；不能把这一轮写成“选定日完全保持”。相应审计和失败事实仍保留。

修复后，改用尚未恢复过的 `recovery-cold-1` 再测：仍是同一 Turn、一轮提问，11月14日东京与11月30日大阪的选定日期全部保持。社区和日期探索调用均未增加，只增加4次验价，实际恢复用时15.766秒；原文取得时间全部保持，两条路线均获得双渠道报价，状态仍为 `partial`。

见[修复后的恢复前事实](../../reports/recovery/resume-fixed-before.json)、[完整审计](../../reports/recovery/resume-fixed-audit.json)和[前后对照](../../reports/recovery/resume-fixed-summary.json)。没有重扫日期、重新提取候选或重新安排初始查询。总墙钟时间包含两段执行之间的等待，不能当作本次恢复耗时。
