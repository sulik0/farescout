# CDP 断线、首次日志与原轮次恢复

后续工作已调整为[独立浏览器会话稳定性专项](browser-session-stability.md)：优先验证 managed profile 的登录保留和自动恢复，不再把日常 Chrome 的 CDP 长期不断开作为主目标。下文保留前一轮真实测试与改动记录。

2026-10-06 更新。真实测试在 10 月 4 日进行；10 月 6 日补齐失败分类、回归测试和日常连接的日志版配置。以下把已经观察到的结果和仍需验证的部分分开说明。

## 当前结果

不睡眠时，两次真实小红书查询都读到正文，用时分别为 48.468 秒和 43.955 秒。中间停止浏览器操作一分钟，之后仍复用同一个 daemon、Chrome 主进程、endpoint 和 TCP 连接。用户确认这两次查询之间没有再次出现授权弹窗。

分别对日常 Chrome 和 managed Chrome 发起一次用户同意的 `pmset sleepnow`。一分钟后的状态检查都显示原连接已断开。日常 Chrome 的 daemon、Chrome PID 和 endpoint 没变；managed 的 daemon 没变，但由 socai 启动的 Chrome 进程已不在。两组测试都没有调用 `socai stop`。

这支持把睡眠或进入睡眠前的系统动作作为主要排查方向，但不能据此断言“操作系统睡眠直接关闭了 WebSocket”。本次导出的电源日志没有取得完整 Sleep/Wake 记录，只能确认发出了睡眠请求，以及请求前后发生了上述变化。此前午间的检查则取得了 `Idle Sleep` 记录，详见[原始断线排查](cdp-disconnect-investigation.md)。尚未完成保持唤醒三小时的长时间对照。

授权后的自动恢复已经在真实研究中成功过一次。原研究从 `blocked` 变成 `partial`，仍使用同一个 Session 和 Turn，获得 3 篇社区正文和 5 条有报价的航线。不过恢复期间还有新的来源失败和后续断线记录，不能把这次恢复成功写成“连接稳定性已经全部通过”。

## FareScout 怎样暂停和恢复

1. 社区命令失败时，先保留已经读到的正文。通用 `CLI_FAILED`、无效返回或读取超时之后，再做一次只读状态检查；只有检查明确显示 CDP 已断开，才按浏览器断线处理。状态检查失败时不会用旧状态假装已经确认断线。
2. 当前轮次保存已经完成的查询、正文读取时间、航线、日期覆盖和报价。只读了一部分帖子的查询不会被标为全部完成。恢复时可以重新取得该查询的搜索卡片，但已读正文不再打开，原时间不变。
3. 研究结束后如果确认浏览器断开，工作台进入等待状态。默认每 5 秒调用一次 `socai status --json`，最多等待 10 分钟。这些检查不发起新的 CDP 连接，也不刷新社区页面。
4. 用户点击“重新连接并继续”时，FareScout 发出一次零正文的只读搜索请求来建立连接。**这是一次 CLI 请求；socai 0.6.1 内部仍可能尝试三次握手**，不能把它描述为底层只连接了一次。
5. 用户在 Chrome 中确认、daemon 报告连接可用后，后台自动续跑原轮次，无需再点一次恢复。事件流持续显示等待和续跑过程；等待时刷新页面也会重新订阅进度，不会另建研究。服务重启后会读取尚未过期的等待记录，继续检查连接。
6. 等待超时后保留研究，用户可以稍后再恢复。开始新研究会取消原等待任务；重复点击连接按钮不会启动两个任务。关闭服务后，迟到的连接回执也不能启动新研究。

如果 CDP 正常，而小红书页面要求登录或限制访问，程序不会自动重跑研究来假装“修复了 Chrome”。用户需先处理页面上的登录或访问问题，再继续。

以上自动等待属于 Web 工作台；CLI 的 `resume` 仍由用户明确执行。同一个数据目录应只运行一个工作台实例，当前没有跨进程研究调度器。

## 首次 WebSocket 终止日志

原 socai 的 WebSocket 读取循环结束时没有独立日志。稍后的状态轮询只能看到 `CDP session is closed`，因此丢失了最早的传输信息。本次对官方 **v0.6.1** 添加了两份小补丁，没有迁移 Runtime，也没有改变浏览器操作范围。

- `v0.6.1-websocket-terminal.patch`：在收到关闭帧、接收错误、发送错误、流结束或本地命令通道结束时立即记录 `cdp_ws_terminal`。每条连接只记录一次终止事件。字段包括 daemon PID、连接序号、连接存活时长、未返回命令数、关闭码，以及 IO / 协议错误类别。
- `v0.6.1-isolated-config.patch`：增加可选 `SOCAI_CONFIG_PATH`，让实验 daemon 使用独立配置。原版 `SOCAI_HOME` 只隔离 daemon 文件，不隔离 `~/.socai/config.json`；不能仅设置它就声称已经隔离 Chrome 配置。

日志不保存 WebSocket URL、关闭原因原文或页面正文。FareScout 读取这些日志时只接受已知类别和数字字段，不把任意日志值公开给界面。

managed 睡眠组在北京时间 **19:11:16.554** 记录到首个 `websocket_receive_failed`，当时 `pending_commands=0`，比随后状态轮询的“会话已关闭”更早。该轮使用最初的日志版，还没有错误子类别；后来补齐了 `error_class`，不能用新代码补造旧日志缺失的原因。

实验 daemon 安装更细日志并重连后，在 **19:18:41.128** 又记录到接收错误，这次类别为 `protocol`、未返回命令数仍为 0。两次查询后的即时状态检查曾显示连接正常；约六秒后才出现这条终止日志。该类别只能说明 WebSocket 接收遇到协议错误，不能确认是 Chrome 退出、系统动作还是其他原因。已导出的字段见 [`managed-first-terminal.json`](../../reports/cdp-stability/managed-first-terminal.json)。

另有真实本地 WebSocket 测试：服务端在没有待返回命令时发出关闭帧，测试确认客户端只记录一次、包含关闭码 1000，并且不输出关闭原因中的私有字符串。这是传输日志测试，不是航班来源验收。

10 月 6 日本机已按计划切换日常 daemon 到日志版，安装记录见 `reports/cdp-stability/diagnostic-install.json`。维护前连接已断开、Chrome 未运行，也没有研究客户端。只结束核对过的旧 PID 7976，没有调用全局 `socai stop`，没有清理浏览器 profile。新 daemon 的版本和构建匹配，状态仍为未连接；本次维护没有主动建立 Chrome 会话。**此次 PID 更换是记录在案的安装操作，不是 10 月 4 日受控测试中发生的意外重启。**

## managed Chrome 的评价

使用独立 `SOCAI_HOME`、独立配置和全新 profile，未复制日常 Chrome 的 cookies。用户在新窗口完成了登录操作。

managed Chrome 通过独立 profile 的本地调试端口建立连接，降低了对日常 Chrome 调试授权流程的依赖。但本次睡眠后仍断开，由 socai 启动的 Chrome 进程也消失了。随后计划重启了**仅实验用的** daemon，以加载更细的日志；新 Chrome 可以启动并连接，两次调用间仍复用同一 TCP 连接。

重新连接后的两次社区调用分别用时 131.900 秒和 20.512 秒，均遇到登录或访问限制，没有读到有效正文。因此不能确认登录态在断线和重启后可靠保留，也不能区分是登录未保留、登录窗口不一致还是平台限制。实验 profile 位于会同步的工作区，同期发生 iCloud 文件问题，进一步限制了这组比较的可信度。

**当前继续默认使用日常 Chrome，不自动切换 managed。** 下一次 managed 对照应把 profile 放在不经云同步的固定本地目录，重新登录后再测睡眠、重连和正文读取。即使验证通过，也仍需原轮次恢复机制，不能靠换 profile 保证 WebSocket 永不断开。

## 构建、启用和重复测试

已有 Rust 工具链时，可执行：

```sh
./scripts/build-socai-diagnostic.sh /private/tmp/farescout-socai-diagnostic-build
```

脚本校验固定官方归档、应用补丁并执行日志测试，不替换正在运行的 daemon。官方标签的 Cargo.lock 与清单不一致，初次 `--locked` 构建失败；仓库保存了成功构建时解析出的锁文件，后续构建使用它并要求 `--locked`。补丁和锁文件见 `patches/socai/`。

将构建产物保留在固定本地目录后，在 `.env` 配置 `SOCAI_BIN`。CLI 与运行中 daemon 的构建不同时，FareScout 会停止来源调用，避免 socai 隐式重启连接。先结束正在进行的研究、保存检查点，再明确维护对应 daemon；**不要用 `socai stop` 清理实验**，v0.6.1 的该命令会扫描其他目录的辅助进程。建立新连接仍需遵守 Chrome 的确认流程。

需要日志包含连接建立记录时，启动 daemon 的环境使用 `RUST_LOG=warn,socai::cdp::raw=info`。配置 `FARESCOUT_RECOVERY_WAIT_SECONDS` 可以调整工作台等待时间，默认 600 秒，范围 15～1800 秒。

不睡眠复用测试：

```sh
PYTHONPATH=src .venv/bin/python scripts/probe-socai-reuse.py \
  --calls 2 --interval 60 --output awake.json
```

安排好用户唤醒后，才执行睡眠组：

```sh
PYTHONPATH=src .venv/bin/python scripts/cdp-sleep-control.py \
  --confirm-sleep --output reports/cdp-stability/sleep.json
```

脚本不重连，也不自动批准 Chrome。继续采集当天指定小时的只读诊断，可使用 `scripts/diagnose-socai-connection.py`。managed 组需在调用前同时设置独立 `SOCAI_HOME` 和 `SOCAI_CONFIG_PATH`；后者只由这份诊断补丁提供。

启动工作台仍使用 `./scripts/run-this-machine.sh serve --port 8768`。项目代码、运行依赖和浏览器 profile 应保留完整本地内容；如果 Finder 显示云端占位，先下载并保留，避免空文件导致启动或 CLI 失败。
